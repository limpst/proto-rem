# 07. 확장 설계 — 프로토타입에서 1만 사용자까지

> 지금은 **프로토타입**입니다. 이 문서는 "나중에 다시 짜지 않기 위해 지금 지켜야 할 경계"를
> 정리한 것이지, 지금 당장 전부 구현하자는 뜻이 아닙니다.
> 프로토타입 단계에서 과설계하면 검증 속도가 죽습니다.

---

## 1. 현재 구조와 그 한계

```
┌─────────────────────────────────────────────┐
│  브라우저 (public/app.js)                     │  ← View
│  화면 · 진행률 폴링 · 사람 결정(HITL 3곳)       │
└──────────────────┬──────────────────────────┘
                   │ HTTP/JSON
┌──────────────────▼──────────────────────────┐
│  py/server.py                                │  ← Controller + Engine 혼재
│  라우팅 · 백그라운드 작업 · 파이프라인 실행      │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│  SQLite (data/proto-rem.db)                  │  ← Model(저장)
└─────────────────────────────────────────────┘
```

**한계 세 가지**

| # | 한계 | 언제 터지는가 |
|---|---|---|
| L1 | 서버 한 프로세스가 라우팅과 AI 실행을 같이 한다 | 동시 사용자 10명만 돼도 서로의 작업을 기다린다 |
| L2 | 작업 큐가 프로세스 메모리(`_JOBS`)에 있다 | 재시작하면 진행 중 작업이 통째로 사라진다 |
| L3 | SQLite 단일 파일 | 쓰기가 직렬화된다. 동시 쓰기가 늘면 잠금 대기 |

## 2. 3-tier / MVC — 지금 지켜야 할 경계

계층을 **파일 단위로** 갈라 둡니다. 나중에 프로세스를 갈라도 코드를 다시 쓰지 않기 위해서입니다.

| 계층 | 지금 위치 | 책임 | 하지 말아야 할 것 |
|---|---|---|---|
| **View** | `public/app.js`, `index.html` | 표시, 사람 입력, 진행률 | 업무 규칙 판단 |
| **Controller** | `py/server.py` 의 `route()` | HTTP 해석, 권한, 작업 시작/조회 | AI 호출, 문안 작성 |
| **Service(엔진)** | `enrich · classify_ai · copy_ai · generate · resolve · deliver` | 업무 규칙, AI 호출 | HTTP, DB 스키마 |
| **Model** | `store · site_store · upsert · domain · sector_fallback` | 저장·조회, 도메인 상수 | 화면 문구 |

### 지금 이미 지켜진 것

- 도메인 지식이 `domain.py` 한 곳에 모여 있다 (고객군·페르소나·분류)
- 저장은 `store.py` 뒤에 숨어 있다. 호출부는 `load/save/update` 세 개만 안다
- 프런트는 `full_state()` 하나만 받는다. 엔드포인트가 늘어도 화면 계약이 안 흔들린다

### 지금 어기고 있는 것 — 다음에 고칠 것

`route()` 안에 파이프라인 실행 로직이 그대로 들어 있습니다.
`/api/enrich` 의 `work()` 가 크롤·AI·저장을 전부 합니다.

**고치는 방향** — `py/pipeline/` 로 뽑아냅니다.

```python
# py/pipeline/enrich.py
def run(tenant: str, card_ids: list[str], *, force: bool = False,
        progress: Callable[[int, str], None]) -> EnrichResult:
    """HTTP 를 모른다. 작업 큐도 모른다. 입력과 출력만 안다."""
```

이렇게 두면 **같은 함수를 HTTP 핸들러가 부르든, 워커 프로세스가 부르든 동일**합니다.
엔진 분리는 그다음에 배치만 바꾸면 됩니다.

## 3. 엔진 분리 — 왜, 언제

### 왜 분리하는가

AI 호출은 **한 건에 수십 초~수 분**입니다. 웹 요청과 같은 프로세스에 있으면
사용자 한 명의 문안 생성이 다른 사용자의 화면 조회까지 막습니다.

지금은 스레드로 피하고 있지만(`ThreadingHTTPServer` + 작업 스레드),
파이썬 GIL 때문에 CPU 바운드가 섞이면 한계가 있고, 무엇보다 **재시작에 약합니다.**

### 목표 구조

```
                    ┌──────────────┐
   브라우저  ───────▶│  API 서버     │  요청당 수십 ms 안에 끝난다
                    │  (여러 대)    │  작업은 큐에 넣기만
                    └──────┬───────┘
                           │ enqueue
                    ┌──────▼───────┐
                    │  작업 큐       │  Redis / RabbitMQ
                    │  (영속)       │  재시작해도 안 사라진다
                    └──────┬───────┘
                           │ dequeue
              ┌────────────┼────────────┐
        ┌─────▼─────┐┌─────▼─────┐┌─────▼─────┐
        │ 엔진 워커  ││ 엔진 워커  ││ 엔진 워커  │  수평 확장
        │ 리서치     ││ 생성      ││ 발송      │  종류별로 따로 늘린다
        └─────┬─────┘└─────┬─────┘└─────┬─────┘
              └────────────┼────────────┘
                    ┌──────▼───────┐
                    │  PostgreSQL   │
                    └──────────────┘
```

**종류별로 나누는 이유**: 리서치는 네트워크 대기가 길고, 생성은 AI 토큰이 비싸고,
발송은 초당 한도가 있습니다. 성격이 다르니 늘리는 속도도 달라야 합니다.

### 언제 하는가

| 시점 | 신호 | 조치 |
|---|---|---|
| 지금 (프로토타입) | 사용자 1~2명 | **그대로 둔다.** 스레드로 충분 |
| 파일럿 | 동시 5~10명, 재시작 시 작업 유실이 불편 | 작업 큐만 Redis 로. 워커는 같은 머신 |
| 초기 SaaS | 동시 50명+ | 워커를 별도 프로세스/컨테이너로 분리 |
| 1만 사용자 | — | 워커 종류별 오토스케일, DB 읽기 복제 |

> **지금 하지 말 것**: 사용자 2명인데 Redis·Celery·Docker Compose 를 깔면
> 검증할 시간에 인프라를 붙들게 됩니다.

## 4. 데이터 — SQLite 에서 어디까지 가는가

### 지금: SQLite 파일 DB

```
data/proto-rem.db
├── meta   (tenant, key, value)     설정·시나리오 기록·홈페이지 보관본
└── cards  (tenant, id, ...)        명함 · 분류 · 근거 · 문안 · 발송이력
```

**모든 데이터가 이 파일 하나에 영구 저장됩니다.** 브라우저를 새로고침해도,
서버를 껐다 켜도 그대로입니다. 백업은 이 파일 하나만 복사하면 됩니다.

### SQLite 로 어디까지 가능한가

읽기는 아주 많이 견딥니다. **쓰기가 직렬화**되는 것이 한계입니다.
WAL 모드를 쓰고 있어 읽기·쓰기가 동시에 가능하지만, 쓰기끼리는 줄을 섭니다.

| 규모 | SQLite | 판단 |
|---|---|---|
| 사용자 1~10 · 명함 1만 | 충분 | 지금 |
| 사용자 ~100 · 명함 10만 | 가능 (쓰기 배치 필요) | 파일럿까지 |
| 사용자 1,000+ | **한계** | PostgreSQL 로 |

### PostgreSQL 이전 — 지금 준비된 것

`cards`/`meta` 두 테이블 모두 **`tenant` 컬럼을 처음부터** 두었습니다.
이전할 때 스키마를 다시 짜지 않아도 되고, Row Level Security 로
테넌트 격리를 DB 차원에서 걸 수 있습니다.

```sql
ALTER TABLE cards ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON cards
  USING (tenant = current_setting('app.tenant'));
```

`store.py` 뒤에 숨겨 두었으므로 **바꾸는 파일은 그 하나**입니다.

## 5. 1만 사용자에서 실제로 문제가 되는 것

인프라보다 먼저 터지는 것들입니다.

| # | 문제 | 지금 상태 | 해야 할 일 |
|---|---|---|---|
| P1 | **AI 비용** | 명함당 리서치 1회 + 생성 1회 | 회사 단위 캐시(했음) · 배치 · 저가 모델로 1차 선별 |
| P2 | **발송 한도** | Gmail 개인 계정 (일 500통) | 전용 발송 서비스(SES·Sendgrid) · 도메인 인증(SPF/DKIM/DMARC) |
| P3 | **수신거부 관리** | 문구만 삽입 | 수신거부 DB · 발송 전 대조 · 재발송 차단 |
| P4 | **개인정보** | 로컬 파일 | 암호화 저장 · 접근 로그 · 파기 정책 · 위탁 계약 |
| P5 | **인증** | 없음 | 로그인 · 테넌트별 권한 · 감사 로그 |
| P6 | **동시 편집** | 마지막 저장이 이김 | 낙관적 잠금(버전 컬럼) |

> **P2·P3·P4 는 기술 문제가 아니라 사업 요건입니다.**
> 1만 사용자가 하루 10통씩 보내면 하루 10만 통입니다.
> 그 규모에서 수신거부와 스팸 신고를 관리하지 못하면 도메인 평판이 죽고,
> 그러면 인프라가 아무리 좋아도 메일이 스팸함으로 갑니다.

## 6. 단계별 계획

### Phase A — 지금 (프로토타입 검증)

- [x] 7단계가 끝까지 도는 것
- [x] 전 구간 fallback (어디서 실패해도 다음 단계로)
- [x] SQLite 영구 저장
- [x] 회사 단위 홈페이지 분석 보관
- [ ] 실제 발송 1건 성공

### Phase B — 파일럿 (사내 1~5명)

- [ ] `py/pipeline/` 로 엔진 함수 분리 (HTTP·큐를 모르는 순수 함수)
- [ ] 작업 큐를 DB 테이블로 (재시작 시 이어받기)
- [ ] 수신거부 목록 + 발송 전 대조
- [ ] 발송 이력 리포트 (응답률·스팸신고율)

### Phase C — 초기 SaaS (외부 10~100명)

- [ ] 로그인 · 테넌트 격리 (RLS)
- [ ] PostgreSQL 이전 (`store.py` 만 교체)
- [ ] 워커 프로세스 분리 (리서치 / 생성 / 발송)
- [ ] 전용 발송 서비스 + 도메인 인증
- [ ] 사용량 계량 → 과금

### Phase D — 확장 (1,000~10,000명)

- [ ] 워커 종류별 오토스케일
- [ ] 읽기 복제 · 캐시 계층
- [ ] AI 비용 최적화 (모델 라우팅 · 프롬프트 캐시)
- [ ] 관측 (작업 지연·실패율·비용 대시보드)

## 7. 지금 코드에서 지켜야 할 규칙

새 기능을 넣을 때 이것만 지키면 위 계획이 그대로 성립합니다.

1. **업무 규칙을 `route()` 안에 쓰지 않는다.** 서비스 모듈에 함수로 만들고 호출만 한다
2. **저장은 `store` / `site_store` 를 통해서만** 한다. SQL 을 다른 파일에 쓰지 않는다
3. **모든 테이블에 `tenant`** 를 둔다. 지금 한 명이어도
4. **오래 걸리는 일은 작업(job)으로** 만든다. HTTP 응답을 붙잡지 않는다
5. **실패는 예외로 끝내지 않는다.** 표준값으로 대체하고 다음 단계로 간다
6. **추정과 사실을 화면에서 구분한다.** ⬇ 가져온 값 / ✧ AI 추정 / ∑ 계산 / ✎ 직접 입력

마지막 규칙이 가장 중요합니다. 나머지는 느려지거나 비싸지는 문제지만,
이것을 어기면 **확인하지 않은 문장이 고객에게 나갑니다.**
