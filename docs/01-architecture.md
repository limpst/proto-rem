# 01. 시스템 아키텍처

## 1. 설계 원칙

| 원칙 | 내용 | 이유 |
|---|---|---|
| **A1. 멀티테넌시 우선** | 1일차부터 모든 도메인 테이블에 `tenant_id`. 단일 사용자 프로토타입도 `tenant_id=1`로 동작 | 나중에 SaaS로 붙일 때 스키마 재작성이 가장 비싼 비용 |
| **A2. 파이프라인 = 상태기계** | 연락처는 `NEW → ENRICHED → SCORED → DRAFTED → APPROVED → SENT → REPLIED`를 이동. 각 전이는 멱등 | 크롤링·LLM은 실패가 정상. 중단 지점부터 재개 가능해야 함 |
| **A3. 어댑터 경계** | 수집원(리멤버/CSV/구글시트), LLM(Claude), 발송채널(메일/문자/카톡)은 전부 인터페이스 뒤 | 리멤버 UI 변경·채널 추가가 코어를 흔들지 않게 |
| **A4. 사람이 최종 발송** | 생성은 자동, **발송 승인은 사람**이 기본값. 자동발송은 옵트인 기능 | 법적 리스크와 브랜드 리스크의 최종 차단선 |
| **A5. 근거 보존(Provenance)** | 모든 생성 문장은 출처 URL·추출 스니펫과 함께 저장 | 환각 방지, 영업사원의 신뢰, 감사 대응 |
| **A6. PII 격리** | 명함 원본은 별도 스토리지·암호화, 로그·프롬프트에는 최소 필드만 | 개인정보보호법 |

## 3. 기술 스택 결정

| 레이어 | 선택 | 근거 |
|---|---|---|
| 수집 | **Playwright (Node)** | 리멤버는 SPA + 로그인 필요. 영속 프로필로 세션 재사용 |
| DB | **PostgreSQL** (프로토타입은 SQLite 호환 레이어) | 멀티테넌시 RLS, JSONB, pgvector 확장까지 한 엔진에서 |
| LLM | **Claude (claude-opus-5 / claude-sonnet-5)** | 리서치 요약·메시지 생성. 대량 저비용 구간은 sonnet, 최종 문안은 opus |
| 대시보드 | **Next.js + TypeScript + Tailwind** | SaaS 전환 시 인증·과금·멀티테넌트 라우팅 생태계가 가장 두터움 |
| 작업큐 | 프로토타입: 파일 기반 잡 → 이후 **Redis + BullMQ** | 초기 과설계 회피, 인터페이스만 미리 분리 |

## 4. 멀티테넌시 설계 (SaaS 대비)

- 모든 테이블에 `tenant_id UUID NOT NULL`, PostgreSQL **Row Level Security**로 강제
- 리멤버 세션은 테넌트별 격리된 프로필 디렉터리 (`.auth/<tenant_id>/`)
- 사용량 계량 포인트를 처음부터 기록: `enrich_count`, `llm_tokens`, `send_count` → 이후 과금 플랜의 근거
- 요금제 가설: Free(연락처 100) / Pro(2,000 + 발송) / Team(팀 명함첩 연동 + 다중 사용자)
